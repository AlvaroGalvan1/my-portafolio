Branches

main     ●──────────── v1 stays live (fixes only) ─────────────●── launch: v2 goes live
          \                        merge main in, now and then ↓    /
v2.0       ●───●───────●───────●───────●───────●───────────────●   staging preview URL
                \     /  \    /  \    /
feat/-…       ●──●     ●──●    ●──●      one ticket each, PR into v2.0
  • Production stays v1. main only gets fixes. Vercel gives v2.0 its own preview URL to check progress.
  • Feature PRs target v2.0, not main. Set the PR's base branch when you open it.
  • Gotcha: Closes #n only closes an issue when the PR merges into the default branch. PRs into v2.0 won't close theirs, so close them by hand or group them in a "v2 launch" milestone.
  • Stay in sync: when main gets a fix, merge main into v2.0 so launch day has no surprises.
  • Old code: each PR deletes the v1 code it replaces. No dead code piles up.
  • Safety net: tag main as v1 before the final merge. Git keeps the rest.

Modular rules

  • One folder per section, with its component and its own copy file. Sections import from ui/ and nothing else.
  • Delete test: removing a section's folder breaks exactly one import line, the one in its page.
  • Stubs first: the Shell ticket creates every page and an empty component for every section. Wave 2 chats only fill in their own folder, so parallel PRs don't conflict.
  • Server by default: only the small interactive part uses "use client", such as the marquee's pause or the active step.

How the chats work together

  • One epic issue ("Portfolio v2") with a sub-issue per ticket and a "v2 launch" milestone. The epic's checklist shows progress.
  • Each issue stands alone: why, what's in and out of scope, which folder, done-when checks, and base branch v2.0. A fresh chat needs nothing else.
  • Build chats: each takes one issue and opens one branch and one PR into v2.0.
  • This chat: reviews every PR against the spec, the skeleton and the issue's scope. You merge.
